### Unit 3 — F02 Resource capacity guard

Contract: `docs/features/f02-capacity.md` → *Technical contract* (design by `architect`, approved by the user 2026-11-05) plus ADR [0002](adr/0002-f02-capacity-token-on-user-concurrencystamp.md) (**Accepted**). Status **Planned**.

**Design**

- **Token (D7)** [SIGN-OFF] — reuse `Users.ConcurrencyStamp` (already `IsConcurrencyToken()`, `UserConfiguration.cs:14`); no column added. Move/Assign load the target assignee **tracked** and set `ConcurrencyStamp = Guid.NewGuid().ToString()` in the same single `SaveChanges()` as the task update + history (+ notification). Bumped only when the write makes the task occupy a slot it did not occupy for that user (Move along a `ConsumesCapacity` edge; Assign of an `InProgress` task to a different user). **Read the assignee (token) before counting** — reversing the order lets a stale count pair with a fresh token.
- **Count** — one query: `AssigneeId == target && Status == InProgress && Id != task.Id`, soft-deleted rows excluded by the query filter (D2, D3, D6, AC20); refuse when `count >= limit`. New index `IX_Tasks_IsDeleted_AssigneeId_Status` (`IsDeleted` leads, T1 convention), migration `AddTasksAssigneeStatusIndex` — **Additive** (CREATE INDEX only, online; `IX_Tasks_AssigneeId` untouched).
- **Rule declaration** — `BE/TaskFlow.Common/Constants/TaskCapacityRule.cs` beside `TaskOverdueRule`: `OccupiesSlot(status)` (InProgress) and `AssigneeRequiredWhile(status)` (InProgress, Review). One private helper in `TaskService` performs load-token → count for both Move and Assign; each maps the result to its own code. No role or permission reaches the check (D4).
- **Limit (D1)** — `ConfigKeys.Workflow.MaxInProgressPerAssignee = "Workflow:MaxInProgressPerAssignee"`, value `3` in `appsettings.json`; startup fails if missing or < 1 (CORS precedent, `Program.cs`); read in `TaskService`'s constructor like `_timeZone`.
- **Order** — Move: existence → version → same-status → transition → actor rule → `RequiresAssignee` (`AssigneeRequired`; also when the assignee row no longer resolves) → capacity. Assign: existence → version → clearing while `AssigneeRequiredWhile` (`AssigneeRequired`) → target exists (`AssigneeNotFound`, AC17) → capacity when `OccupiesSlot(task.Status)` and target ≠ current assignee (AC9 no-op skips the check and the bump).
- **R13** — F02 adds S-locks on the Users row via FKs (`TaskHistories.ActorUserId` when actor = assignee, `TaskNotifications.RecipientUserId` on rework, `Tasks.AssigneeId` on assign) followed by the X-lock `UPDATE Users`: the same lock-upgrade deadlock. Handled by the existing two-catch in `Move`/`Assign` (`TaskConcurrencyHelper.IsDeadlock`, unchanged) → the operation's existing `…Conflict`, `Warning`. No retry (no `EnableRetryOnFailure`, no application retry).
- **Contract** — new codes in `TaskControllerMS` (names reserved in F01 T3), all 400: `Task.Move.AssigneeRequired` (AC11) · `Task.Move.CapacityReached` (AC2, AC6, AC22) · `Task.Assign.AssigneeRequired` (AC12, AC13) · `Task.Assign.CapacityReached` (AC7, AC22). AC17 reuses `Task.Assign.AssigneeNotFound` / `Task.Create.AssigneeNotFound`. [SIGN-OFF] For `*.CapacityReached` the envelope's `error` is formatted from `TaskControllerMS.Templates.CapacityReached` with the assignee's userName and the configured limit (AC2, AC19); Move/Assign service tuples gain `string? ErrorMessage` (internal, not a wire change). The AC18 loser gets the existing `…Conflict`. No request/response field changes; nothing breaking.
- **Users list** — `GET api/v1/users` → `ResultRes<List<UserRes>>` `{ id, userName, role }`, policy `ViewTasks`, soft-deleted excluded, ordered by userName, `UserControllerMS.GetList.Exception` (already approved, sign-off #6; never built).

## Order and parallelism

1. **Agree the API contract for a unit before either side starts it.** API and client are built in parallel, so route, verb, request fields, response shape, error codes and auth policy are written down first — see the constraint in `CLAUDE.md`.
2. Unit 0 first, then F01 + F04 together as one unit, then F02, then F03, then F05.
3. The client can start against the agreed contract while F01 is in progress; it does not wait for the API to be finished.
4. There is one working tree, so one slice branch is checked out at a time and build slices run in sequence. Read-only work — the architect's F01 + F04 design — runs concurrently with a build slice, because it edits no files.

## Decisions already locked (2026-10-20)

All 26 open questions raised during planning are answered; the specs state them as rules under each file's **Decisions** heading. The ones that cut across features:

- One shared board — no team entity, no row-level filtering; every authenticated user sees every task.
- Members may view, create, update, move and assign **any** task; delete and reopen are Manager / Admin only.
- Leaving `Review` must be done by someone other than the current assignee. On a one-person board a task therefore stays in `Review` — accepted, and written down as a rule.
- `DueDate` is a `DateOnly`; "today" is resolved in `Asia/Ho_Chi_Minh` from configuration; timestamps stay UTC.
- Overdue covers every task that is not `Done`, `Backlog` included.
- The board is drag-and-drop: dropping a card changes status only, and the drop position carries no meaning.

Tests, users, the drag-and-drop library, CI and the git rule were decided on 2026-10-25: `CLAUDE.md` → *Decided before F01*.

| R13 | f01-workflow.md T2 describes AC29's mechanism as "the second writer blocks on the InnoDB row lock, re-reads under it, matches 0 rows, and EF raises `DbUpdateConcurrencyException`" — true sometimes, but two genuinely concurrent writers against the same row can also make InnoDB pick one transaction as a **deadlock victim** (MySQL error 1213). **Root cause, confirmed by `SHOW ENGINE INNODB STATUS`'s `LATEST DETECTED DEADLOCK` section against a standalone repro of the exact two statements `Move` issues:** within one `SaveChanges()`, EF Core/Pomelo emits the `INSERT INTO TaskHistories` (the Added entity) **before** the `UPDATE Tasks` (the Modified entity) — there is no key-generation dependency forcing the opposite order, since `TaskId` is already a known existing value, not one this batch generates. The FK `TaskHistories.TaskId → Tasks.Id` (`ON DELETE RESTRICT`) makes InnoDB take an implicit **shared (S), no-gap** record lock on the referenced `Tasks` row for every `INSERT` that references it, regardless of isolation level. Two concurrent transactions T1/T2 both run their `INSERT` first and both successfully acquire that **S**-lock on the same `Tasks` row (S-locks are mutually compatible). Each then reaches its own `UPDATE Tasks … WHERE Id=@id AND Version=@original`, which must **upgrade** its own S-lock to **X** (exclusive) on that same row — T1 waits on T2's S-lock, T2 waits on T1's S-lock: a textbook two-party lock-upgrade deadlock, confirmed line-for-line in the captured dump (both transactions shown `HOLDS` an `S` lock and `WAITING FOR` an `X` lock on the identical `Tasks` primary-key record). Reversing the two statements in the standalone repro (`UPDATE` before `INSERT`) never deadlocked across 8 runs; the original order (matching what EF actually emits) deadlocked on the first run. Pomelo's non-retrying execution strategy then wraps the `MySqlException` two levels deep — inside an `InvalidOperationException` inside a `DbUpdateException` — so a `catch (DbUpdateConcurrencyException)` alone never sees it | `TaskFlow.BusinessLogic/Services/TaskService.cs` (`Move`) | A mutating operation that only catches `DbUpdateConcurrencyException` around its `SaveChanges()` will let a deadlocked concurrent write surface as an unhandled 500 instead of the operation's `…Conflict` code — the exact failure AC29/AC30-style tests are meant to catch. **No avoidance was found that fits within "no contract change, no explicit transaction, statement order only" (investigated and rejected):** (1) splitting into two `SaveChanges()` calls (task update committed, then history/notification) would need an explicit transaction to keep AC31's atomicity, which is out of scope here and changes the established "exactly one `SaveChanges()`" pattern; (2) reordering the C# calls that mutate the task vs. `Add()` the history has **no effect** — the real deadlock repro proves the emitted SQL order is an EF/Pomelo batch-ordering detail, not a function of source-code statement order, so this cannot be fixed by reordering application code; (3) dropping the FK on `TaskHistories.TaskId` would remove the lock trigger but weakens `database.md`'s "every reference is a real foreign key" integrity rule — a schema/architecture decision needing its own review, not a quick fix. **Decision: accept it as a known, benign MySQL/InnoDB behavior under real concurrent writes and keep handling it as implemented** (catch + map to `…Conflict`, logged at `Warning` since it is an expected outcome, not a defect) — this is what slice 1.2 ships. **Reopen and assign (1.3, 1.4) must catch both failure modes the same way move does:** `catch (DbUpdateConcurrencyException)` plus an unwrapped-exception-chain check for MySQL error 1213, logged at `Warning`. **Note for F02:** the capacity guard's concurrency token (a count-guarded owning row, `backend.md` §4 Recipe 14) writes an `UPDATE` on the owning row alongside other inserts in the same commit and will hit the identical lock-upgrade pattern under real concurrent assigns if any FK-child insert in that commit references the same row — budget for the same two-catch pattern, not `DbUpdateConcurrencyException` alone, and do not assume reordering the service's C# statements changes the emitted SQL order. **Logging:** `Serilog:MinimumLevel:Override` in `BE/TaskFlow.Api/appsettings.json` now sets `Microsoft.EntityFrameworkCore.Update` to `Fatal` — EF logs every `SaveChanges` failure at `Error` under that category *before* the caller gets a chance to handle it (`CoreEventId.SaveChangesFailed`), which duplicated our own handled-deadlock `Warning` as a spurious `[ERR]` line. Raising that one category's floor leaves a handled deadlock as a single `[WRN]` line from `TaskService`; a genuinely unexpected failure still logs at `Error` both from a *different* EF category (`Database.Command`, "Failed executing DbCommand…") and from the controller's own `catch (Exception ex)` (`Logger.LogError(ex, "Move task {Id} failed", id)`, category `TasksController` — unaffected by the override, confirmed by `Move_RealDatabaseFailure_ThroughHttp_ReturnsExceptionCode_NotConflict`, which hard-deletes the acting user's row after login to force a real `TaskHistories.ActorUserId` FK violation through the full HTTP pipeline) | 1.2 — **Done** for move (`TaskService.Move`'s `IsDeadlock` helper, the Serilog override, `BE/TaskFlow.Tests/Http/TasksMoveControllerTests.cs`); reopen, assign and F02's capacity guard still need the two-catch pattern |

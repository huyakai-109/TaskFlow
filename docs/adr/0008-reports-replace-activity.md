# 0008 — Reports replace the Activity feed: metrics derived on read from F04 history, holder-at-Done attribution, Recharts

Status: **Proposed** (design by `architect`, 2026-11-21; awaiting the user's sign-off). Supersedes [0007](0007-keyset-paging-for-activity-feed.md) (its endpoint is removed; its *rule for future lists* stays as guidance).

## Context
The Activity page ([f04-activity-feed.md](../features/f04-activity-feed.md)) re-lists the per-task F04 trail across tasks and adds no insight. The user decided (2026-11-21) to replace it with per-member performance Reports for appraisal ([f09-reports.md](../features/f09-reports.md)): a balanced scorecard (delivery, speed, reliability, quality/load), no composite score, no ranking; Manager/Admin see the team and anyone, a Member sees only their own data, enforced on the server. Every figure must come from rows already stored: `TaskHistories` has no "holder" column, so who held a task at a past moment has to be reconstructed from `AssigneeChanged` entries. The client has no chart library.

## Decision
1. **Computed on read, from `Tasks` + `TaskHistories` only.** No new table, history event, snapshot job or index. `ReportService` reads, no-tracking: the data-available-since date (`MIN(TaskHistories.CreatedAt)`, served by the existing `IX_TaskHistories_CreatedAt_Id`), the candidate tasks (filtered with `IgnoreQueryFilters()` to tasks that could touch the range), their full trails (`IX_TaskHistories_TaskId_CreatedAt_Id`) and user names. A pure `ReportCalculator` (BusinessLogic, no I/O) replays each trail ordered by `(CreatedAt, Id)`. The only migration is `AddReportPermissions` (RoleClaims inserts, **Additive**).
2. **Attribution = the holder at the moment of the event**, never the actor. A completion counts for whoever held the task at its counted `→Done`, never the reviewer who moved it. Because assignment is locked in Review/Done and only the holder may Submit (F01 R2, A1/A3), that is the person who submitted the final version. Take-overs (`AssigneeChanged` with actor = new assignee and a previous holder) are reported per member (taken / lost). A `Done` later followed by `Reopened` does not count; a task counts once, at its last `Done`.
3. **Time:** buckets are calendar days, Monday-start weeks (B7), months and quarters in `Workflow:TimeZone`, and request dates are inclusive local dates. Partial edge buckets are flagged. Conversion always goes through `TimeZoneInfo` (Asia/Ho_Chi_Minh has had no DST since 1975), never a hard-coded +7.
4. **Permissions:** `ViewReports` and `ExportReports` are appended to `Permissions.All` and to the Admin/Manager role lists (seed ids Admin 16/17, Manager 1015/1016). The scorecard and drill-down endpoints use the `ViewTasks` policy, and the service refuses out-of-scope requests with `Report.<Op>.SelfOnly` (the `Task.Assign.SelfOnly` precedent). The team endpoint uses the `ViewReports` policy and export uses `ExportReports`; both return 403 otherwise.
5. **Activity removed:** `GET /activity`, `CursorResultRes`/`CursorPageRes`, `ActivityCursor`, `GetFeed`, their DTOs, mapper and tests, and the FE page, API module, types and error copy. The per-task history endpoint and timeline are unchanged. Drill-down lists use the house offset paging (they are bounded, recomputed lists, which is ADR 0007's own rule). Feed indexes stay; dropping one is not additive.
6. **Charts:** `recharts` **3.10.1** with an exact pin (published 2026-07-25; 3.11.0 was published 2026-11-17, under two weeks before this decision). It is loaded only in the lazily imported `/reports` route chunk. The heatmap is a hand-built HTML table. Every chart has a data-table fallback.
7. **Review wait is its own metric (addresses gap G3), not just a caveat.** `reviewWait` = the counted completion's time minus the `InProgress→Review` entry immediately before it — the length of the final review pass, reusing timestamps already walked for R7 (rework). Reported as a third `Distribution` beside `cycleTime`/`leadTime`, same median/p85/low-sample rules, no new chart (scorecard field only). Chosen over "caveat only" because it is nearly free (same trail walk, same entries, no new query) and because an appraisal tool that silently folds reviewer latency into a holder's cycle time is a correctness problem for the person being appraised, not merely a nuance worth a footnote.
8. **A `Reopened` entry is never a rework submission.** R7 (`f09-reports.md`) originally let a `Reopened` entry re-open a submission whose later `Review→InProgress` counted as `sentBack`, which double-counted one reopen as both `reopenedAfterDone` **and** a rework strike. Fixed before implementation: only a `StatusChanged InProgress→Review` entry opens a submission; a `Reopened` round trip is invisible to `reworkRate` and lives solely in `reopenedAfterDone`.

## Consequences
- Every request recomputes the report. Cost grows with *active plus recently finished* tasks, not with total history age. Assumed scale: ≤ 50 users, ≤ 5 000 candidate tasks, ≤ 100 000 history rows per request. If `EXPLAIN` or timing shows otherwise, an additive index or a cache is a follow-up decision.
- **Known property, stated on the page (not a defect):** past figures can change after the fact — a reopen removes an earlier completion (only the *last* `Done` counts, R3), and a due-date change before Done changes on-time status. A period already shown to someone can read differently later. This is intended and is in both the ADR and SPEC §11.5's caveat text, so it is never discovered as a surprise.
- Capacity utilisation divides by **today's** configured limit. The limit's history isn't stored, so periods before a limit change are approximate. **Superseded 2026-11-22** (see below): Load is now a ticket count, so there is nothing left to divide by the limit.
- **2026-11-22 (user request):** Load (R8) was changed from time-weighted averages (`avgInProgress`/`capacityUtilization`) to an integer `ticketsWorked` count of distinct tasks held in `InProgress`, before any release — counts are legible and auditable by hand the way an average isn't, at the cost of not reflecting how long a task was actually held.
- Breaking API change: `GET api/v1/activity` and the cursor envelope are removed. The only consumer is this repo's FE, removed in the same branch.
- New FE dependency: about 150 kB gzip for the full package (bundlephobia); real cost depends on tree-shaking. It pulls in `@reduxjs/toolkit`, `immer`, `react-redux` and `victory-vendor`, and needs `react-is` as a peer. All of it is kept out of the main chunk.
- Members' session claims pick up a new permission within ≤ 15 min (`Security:Jwt:ExpirationMinutes`), and a demoted Manager keeps team access for the same ≤ 15 min (accepted precedent, f08).

- Export calls are logged with their subject and row count (caller id, `userId`/`"team"`, range, dataset, row count — never content), one layer more detail than the read endpoints, because an export is the one action that leaves the system as a downloadable file.
- **Known simplification, accepted 2026-11-21 (terminology updated 2026-11-22 for the `ticketsWorked` rename, same substance):** R2/R5b/R7's holder and submission reconstruction walk the trail by `(CreatedAt, Id)` **position**, as specified — but the continuous per-user InProgress timeline used only for R8's `ticketsWorked` (splitting an InProgress interval at a holder change) compares by **timestamp**, not index. The two same-timestamp `AssigneeChanged` entries this could mis-order are a rare, low-stakes edge case (it only shifts which half-instant of a task's InProgress time a take-over is attributed to, never which holder gets a completion or rework credit — those are governed by the index-based rule and unaffected). Accepted rather than reworked, and recorded here so it isn't rediscovered as a defect.

## Alternatives rejected
- **Snapshot tables filled by a nightly Quartz job:** a second source of truth, a migration and a job for figures cheap enough to compute on read at this scale; also stale by up to a day.
- **New `Completed`/`HolderAtEvent` history columns or events:** not needed, because the holder can be rebuilt exactly. It would be a schema change to the append-only F04 table, and would leave old rows without the column.
- **Crediting the actor of `→Done`:** that is the reviewer (F01 D5 forbids the holder), so all credit would go to approvers.
- **Splitting credit across holders by time held:** opaque to the people being appraised and impossible to check by hand. Take-over counts make the simple rule visible instead.
- **Reusing the legacy `ManageReports` claim:** the user named `ViewReports`. `ManageReports` stays dead, like Manager's `Members.*` (B8).
- **Chart.js 4.6.1 (~70 kB gzip, canvas):** canvas can't use the `var(--color-*)` tokens, so colours would need re-reading and repainting on every theme switch, and the screen reader gets a bitmap.
- **`@visx/xychart` 4.0.0 (~50 kB gzip):** low-level; keyboard navigation and tooltips would be ours to build and maintain across 4 chart types.
- **Hand-rolled SVG for every chart:** axes, scales, tooltips and keyboard navigation for 4 chart types is a library's worth of code to own. Hand-rolling is kept only for the heatmap, where an HTML table is the more accessible form anyway.
- **Recharts 3.11.0:** under two weeks old on 2026-11-21.
